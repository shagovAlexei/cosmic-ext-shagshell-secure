# 04. Аутентификация: askpass, keyring, ключ хоста

## Зачем

Сейчас ssh спрашивает пароль и подтверждение ключа хоста в терминале, а сохранить пароль нельзя. В SecureCRT это диалоги с «Сохранить пароль», и сохранённый пароль больше не спрашивается. Делаем так же, не реализуя SSH сами: системный ssh зовёт нашу askpass-программу, она спрашивает работающее приложение.

Этап делится на два PR:
- **4a** — askpass, диалоги пароля / passphrase / ключа хоста / прочих запросов, сохранение в Secret Service (keyring), повторный запрос при неверном пароле.
- **4b** — Credentials Manager: именованные наборы логин + пароль, сессия ссылается на набор.

## Как ssh спрашивает (проверено на OpenSSH 9.6)

ssh запускается с `SSH_ASKPASS=<путь к shagshell>`, `SSH_ASKPASS_REQUIRE=force` и вызывает `shagshell "<текст запроса>"` — один аргумент, без подкоманды. Ответ — строка в stdout, код ≠ 0 — отмена. `SSH_ASKPASS_PROMPT` в этих запросах пуст, вид запроса — по тексту:

| Вид | Текст | Диалог |
|---|---|---|
| Пароль | `home@192.168.0.20's password: `, keyboard-interactive `(user@host) Password: ` | поле пароля + «Сохранить пароль» |
| Passphrase | `Enter passphrase for key '/home/u/.ssh/id_ed25519': ` | поле + «Сохранить» |
| Ключ хоста | `The authenticity of host '…' can't be established.` … `fingerprint is SHA256:…` … `(yes/no/[fingerprint])? ` | текст запроса, [Принять и сохранить] (ответ `yes`) / [Отмена] (`no`) |
| Другое (OTP, `Verification code:` …) | что угодно ещё | поле (видимое), без сохранения |

Неверный пароль: ssh спрашивает ещё раз (до 3 раз, `NumberOfPasswordPrompts`) тем же процессом.

## Устройство

- **Приложение** при старте слушает unix-сокет `$XDG_RUNTIME_DIR/shagshell/askpass-<pid>.sock` (в каталоге ControlMaster, 0700; свой на каждый запущенный экземпляр, путь — в env ssh), удаляет его при выходе.
- **Запуск ssh** добавляет env: `SSH_ASKPASS=<свой бинарник>`, `SSH_ASKPASS_REQUIRE=force`, `SHAGSHELL_ASKPASS_SOCK=<сокет>`, `SHAGSHELL_SESSION=<id сессии>` (Quick Connect без сохранения — нет), `SHAGSHELL_TAB=<id вкладки>`.
- **Помощник** — тот же `shagshell`: если задан `SHAGSHELL_ASKPASS_SOCK` и аргумент ровно один — это askpass. Шлёт в сокет одну строку JSON `{prompt, session, tab, ppid}` (ppid — процесс ssh), ждёт ответ `{answer}` или `{cancel}`; печатает ответ, выходит 0 / 1. Нет сокета — код 1 (ssh: отказ), в stderr — причина.
- **Ответ приложения:**
  1. Пароль / passphrase и есть `session`: смотрим keyring (атрибуты `app=io.github.shagovalexei.ShagShellSecure`, `kind=session`, `id=<id сессии>`, `secret=password|passphrase`). Нашли и это первый такой запрос от этого ssh (ppid) — отвечаем без диалога.
  2. Иначе — диалог в главном окне; вкладка запроса становится активной. Второй запрос пароля от того же ssh — диалог «Пароль не подошёл», поле пустое.
  3. «Сохранить пароль» (по умолчанию выключено; только если есть сессия и keyring доступен) — пишем в keyring при OK, заменяя прежний.
  4. Отмена / Esc — `{cancel}`.
- Несколько запросов сразу (Connect all) — очередь, диалог по одному, в заголовке — имя вкладки.
- Вкладка закрыта / ssh завершился, пока висит его диалог — диалог убирается.
- **keyring** (`core::keyring`, Secret Service по zbus, из shagoff-commander): `lookup`, `store`, `delete`, поиск всех наших записей. Заблокирован — gnome-keyring сам спросит пароль разблокировки; недоступен — диалоги работают, «Сохранить» неактивно с подсказкой.
- **Сессия переименована / перемещена** — её записи в keyring переезжают на новый id; **удалена** — удаляются.
- **Session Options → Подключение:** строка «Пароль сохранён» / «Passphrase сохранена» с кнопкой [Забыть], если запись есть.
- Секреты не пишутся ни в файлы, ни в лог, ни в `Debug`-вывод.
- `shagshell --check`: строка keyring (Secret Service отвечает).
- **Отмена** завершает этот ssh (иначе он шлёт серверу пустые пароли за оставшиеся попытки — блокировка на сетевом железе); что процесс наш — по его `/proc/<pid>/environ`.

## Мои решения (проверь)

- Свой сокет на каждый экземпляр приложения (`askpass-<pid>.sock`), а не один `askpass.sock` из архитектуры: два запущенных окна не перехватывают запросы друг друга.
- Passphrase ключа хранится на сессию (как в SecureCRT), не на файл ключа. Если ключ в ssh-agent (gnome-keyring), ssh её и не спросит.
- «Принять один раз» для ключа хоста не делаем: OpenSSH через askpass этого не умеет. Изменившийся ключ ssh отвергает сам, с предупреждением в терминале.
- Повтор «пароль не подошёл» определяем по ppid помощника (процесс ssh): разные вкладки одной сессии не мешают друг другу.

# 4b — Credentials Manager и мастер-пароль

## Наборы учётных данных (как Credentials Manager в SecureCRT)

- Набор: имя + логин + пароль. Сессия ссылается на набор по имени; пароль сменили в наборе — он сменился у всех его сессий.
- Хранение: `~/.config/shagshell/credentials.toml` — только имена и логины (запись атомарная, как сессии):
  ```toml
  [lab-admin]
  user = "admin"
  ```
  Пароль — в keyring: `kind=credential`, `id=<имя набора>`, `secret=password`.
- В сессии поле `credential = "lab-admin"`. Логин тогда берётся из набора (поле «Пользователь» в Session Options неактивно и показывает логин набора), пароль ssh — из набора; диалог пароля сохраняет в набор («Сохранить пароль в «lab-admin»»). Passphrase ключа по-прежнему хранится на сессию.
- Набор указан, но его нет (удалили файл руками) — сессия подключается со своим логином, как без набора.

### Окно Credentials Manager

Отдельное окно (как Session Options), Tools → Credentials Manager… и кнопка в Global Options:

```
 Учётные данные                                        ×
 ┌──────────────┐  Имя:          [lab-admin       ]
 │ lab-admin    │  Пользователь: [admin           ]
 │ core-ro      │  Пароль:       [••••••          ]  (сохранён / не задан)
 │              │                              [Удалить] [Сохранить]
 └──────────────┘
 [+ Новый]                                         [Закрыть]
```

- «Сохранить» — для выбранного набора: имя (проверка как у сессий, уникальное), логин; пароль — только если введён (пустое поле — пароль не меняется).
- Переименование набора — сессии, ссылающиеся на него, переписываются на новое имя, его пароль в keyring переезжает.
- Удаление — подтверждение «Используется в N сессиях»; эти сессии получают логин набора себе в `user` и перестают ссылаться на набор; пароль набора удаляется из keyring.
- В Session Options → Подключение: выпадающий список «Учётные данные»: «(нет)» и наборы по имени.

## Мастер-пароль (отдельная связка keyring)

- Global Options: галочка «Хранить пароли в отдельной связке с мастер-паролем».
- Включение: создаётся связка keyring «ShagShell Secure» — gnome-keyring сам спрашивает её пароль (это и есть мастер-пароль). Наши сохранённые пароли переносятся в неё из основной связки.
- Связка не открывается при входе в систему: при первом обращении за паролем gnome-keyring спрашивает мастер-пароль (как SecureCRT при старте). Отказ — диалог пароля работает как без сохранённого.
- Выключение: пароли переносятся обратно в основную связку, наша удаляется.
- Признак «включено» — само наличие связки с меткой «ShagShell Secure» (без отдельной настройки: настройка и связка не могут разойтись).
- Новые пароли пишутся в нашу связку, если она есть, иначе в основную.

## Мои решения (проверь)

- Логин сессии с набором — из набора (как в SecureCRT), свой логин сессии игнорируется, но не стирается.
- Удалённый набор не ломает сессии: им копируется логин.
- Passphrase не переносится в наборы — она про ключ сессии.
- «Заблокировать сейчас» (запереть связку до следующего мастер-пароля) не делаю — это есть в «Пароли и ключи» (Seahorse).
